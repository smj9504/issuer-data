# 대주주·FI 지분 매각 추적 (DART 원문 파싱)

**Date:** 2026-09-03
**Status:** 구현 완료 (실데이터 검증됨) · 전체 시장 스캔까지 구현·실측 완료.
남은 미해결 항목은 지분 변동 단가 1건뿐이며 이는 제도적 한계다 (HANDOFF.md 참고)

## Question

D001(주식등의대량보유상황보고서)과 자기주식 처분결정/결과보고서 원문에서 매도·매수
거래를 추출해, 매도자/매수자를 분류하고 딜 단위로 집계하며 가격 정합성을 검증한다.

원래 요청은 "대주주-FI 매각"이었지만, 특정 종목·기간·판정기준을 미리 못 박는 대신
**어떤 종목·기간·분류기준에도 적용되는 범용 파이프라인**으로 설계한다.

## 설계 원칙 — 분류를 코드에 넣지 않는다

핵심 결정: **"FI냐 대주주냐"를 파서가 판정하지 않는다.**

실측해보니 DART 원문에 발행사가 신고한 관계 코드가 이미 들어있다:

| 필드 | 코드 예시 | 의미 |
|---|---|---|
| `FLT_CRP_RLT` | `10` / `14` / `16` | 최대주주 / 계열회사등 / 기타 |
| `SPC_TP` | `K` / `I` / `D` | 금융기관 / 국내법인 / 개인(국내) |
| `IFR_RLT` | `I` / `C` / `L` | 최대주주 / 계열회사 / 기타 |
| `HLD_MTH` | `01` / `02` | 장내매수(+) / 장내매도(-) |

보고자명으로 PE/VC를 문자열 추측하면 규칙이 코드에 굳어버리고, 기준이 바뀔 때마다
재수집해야 한다. 대신 **원문의 코드값을 그대로 저장**하고, "FI 판정"은 저장된 뒤
SQL/뷰 층에서 한다. 그러면:

- 기준을 바꿔도 재수집이 필요 없다 (쿼리만 수정)
- 같은 데이터에 여러 정의를 동시에 적용할 수 있다 (엄격/느슨 기준 비교)
- 판정 근거가 원문 코드로 남아 감사 가능하다

이름 기반 휴리스틱이 필요하면 그건 **별도 매핑 테이블**로 두고 파서 밖에 둔다.

정반대 상황 — DART 서식은 고정이라 **결정론적 코드 파싱이 맞고, LLM 추출은 불필요**하다.

## 선결 과제 (블로커)

`kr_dart.py`의 `fetch_filings`가 `kind="A"`(정기공시)로 하드코딩되어 있어 지분공시(D)와
주요사항보고(B)를 **구조적으로 가져올 수 없다**. `--filing-type`으로도 우회 불가 —
애초에 목록에 담기지 않는다. EDGAR `filing_types` 때와 같은 유형의 갭(수집기는 있는데
파라미터가 없음)이므로, 우회 스크립트가 아니라 `kind` 파라미터화로 해결한다.

## 범용화 설계

### 1. 수집 계층 — 파라미터로 열어둔다

- `fetch_filings(..., kind=...)` — A/B/D 등 공시유형 선택 (기본값은 현행 유지)
- 대상 종목은 인자로 받되, 전체 시장 스캔은 `securities` 테이블에서 종목을 얻어
  순회하는 방식 (DART는 회사별 조회가 기본)

### 2. 저장 계층 — 원문 코드를 그대로 보존

새 테이블 2개. 판정 결과가 아니라 **관측된 사실**만 담는다:

- `kr_stake_changes` — D001 변동 명세 1행 = 1거래
  `company_id, rcept_no, reporter_name, reporter_id(사업자번호), reporter_type(SPC_TP),
   relation(FLT_CRP_RLT), change_date, method(HLD_MTH), stock_kind, shares_before,
   shares_delta, price, source` + `source`를 PK에 포함 (기존 컨벤션)
- `kr_treasury_disposals` — 자기주식 처분결정/결과
  `company_id, rcept_no, decided_date, shares, unit_price, total_amount,
   counterparty(DSPS_PARN), purpose(SEL_PPS), report_kind(결정/결과), source`

### 3. 분류·집계 계층 — 뷰로 분리

- 매도/매수 분류: `method` 코드 기반 (`02`=매도 등)
- 딜 단위 집계: `(company_id, change_date, reporter_id)` 로 묶되, 블록딜은 여러
  특별관계자가 같은 날 동시 매도하므로 `rcept_no` 단위 롤업도 병행
- 가격 정합성: 자기주식 `unit_price`와 같은 날 시장가(`prices.close`) 대비 할인율,
  D001 매도와 처분결과의 수량·일자 교차 확인
- "FI 판정"은 여기서 정의 — 파서가 아니라 뷰에서

## 정정공시와 중복 — 조사 결과 문제 없음 (2026-09-04)

"`[기재정정]`이 새 접수번호로 나오니 원본과 중복 집계되지 않겠나"를 확인했고,
**중복은 발생하지 않는다.** 고칠 것이 없으므로 별도 dedup 뷰를 두지 않는다.

실측 (005930, 2024-11 ~ 2025-03 대량보유 보고서 7건 전수 비교):
- `(보고자, 변동일, 방법, 변동수량)` 기준 보고서 간 겹침 **0건**
- 같은 날 접수된 정정본(`20250124000900`)과 일반 보고서(`20250124000908`)조차
  변동일 범위가 12/19~1/10 vs 1/14~1/22로 **이어붙을 뿐 겹치지 않는다**

이유는 서식 자체에 있다. 각 보고서는 **직전 보고 이후의 변동만** 기재하므로 시간축이
분할되지 중복되지 않는다. 정정은 그 구간의 내용을 고쳐 다시 내는 것이라, 정정본이
포함하는 구간을 원본도 담고 있으면 겹치겠지만 — 위 표본에서는 정정본과 원본이 각각
다른 구간을 담았다.

표본 규모: 대량보유 86건 중 정정 4건(4.7%, 8개 종목 2025-01~2026-08). 정정 자체가
드물고, 발생해도 구간이 분할되어 있다.

**남은 위험 (작음):** 정정본이 원본과 *같은 구간*을 재기재하는 경우는 이 표본에
없었다. 전 종목 스윕 후 아래 쿼리로 재확인하면 된다 — 0행이면 그대로 두면 된다.

```sql
SELECT company_id, holder_name, change_date, method, shares_delta,
       COUNT(DISTINCT rcept_no) n, string_agg(DISTINCT rcept_no, ',')
FROM kr_stake_changes
GROUP BY company_id, holder_name, change_date, method, shares_delta
HAVING COUNT(DISTINCT rcept_no) > 1;
```

## 전 종목 스윕 전에 확인한 것 (2026-09-04)

정정공시 외에 다른 문제가 있는지 점검하다 **실제 데이터 유실을 발견해 고쳤다.**

**주식 종류가 키에서 빠져 행이 사라지던 문제 (수정됨)**
한 보고자가 같은 날 같은 방법으로 보통주(`STK_KND=11`)와 기타주식(`10`, 우선주·
신주인수권 등)을 각각 변동 신고하면 별개 행인데, PK에 `stock_kind`가 없어 두 번째가
첫 번째를 덮어썼다. `20260805000440`에서 **파싱 64행 → 저장 60행**, 이석희의 191,684주
변동이 통째로 소실. PK에 `stock_kind`를 넣고, 기존 DB는 `connect()`가 테이블을
재생성해 따라오게 했다. 재수집으로 60→64행 복구 확인.

**`--reparse` 추가** — 접수번호 스킵이 파서·키 수정 후 발목을 잡는다. 저장된 행은
옛 파서의 *출력*이라, 접수번호를 건너뛰면 잘못된 결과가 영구히 남는다. `--restart`는
스캔 커서만 지우므로 별도 플래그가 필요했다.

**요청 기간 밖 데이터가 섞인다 (동작상 문제 없음)**
`--start/--end`는 *접수일*을 거르지 실제 *변동일*이 아니다. 2026-06~08만 요청해도
`20260805000440`이 2022-02-25부터의 이력을 담고 있어 185행 중 43행이 2026년 이전이다.
중복은 아니므로(접수번호 단위 dedup) 데이터 정합성 문제는 없지만, **기간으로 집계할
때는 `change_date`로 필터해야지 수집 범위를 신뢰하면 안 된다.**

## 한계 / 열린 질문

- **가격**: 확인 완료 — D001 변동명세에는 단가 필드가 **아예 없다** (12건 전수에서
  `MDF_UNT_PRC` 0건, `PRH_AMT`(취득자금 총액)만 6/12건). 따라서 지분변동 가격은
  `prices`의 당일 종가로 근사하고, 실제 체결가 검증은 단가가 명시되는 자기주식
  처분(`SEL_OSTK_SPRC`) 쪽에서만 가능하다.

- **관계 코드의 위치**: `FLT_CRP_RLT`/`SPC_TP`는 변동 행이 아니라 **별도 특별관계자
  명부 표**에 있다. 사업자번호(`SPC_ID2`)로 조인해야 하며, 변동 행에서 직접 읽으면
  분류에 필요한 필드가 전부 NULL이 된다 (회귀 테스트로 고정).
- **코드 사전**: 22건 표본으로 넓혀 16개 `HLD_MTH` 코드를 확보했다 (`01`/`02` 장내,
  `11`/`12` 장외, 그 외 신규보고·자사주상여금·주식분할 등). 부호는 라벨 접미사
  `(+)`/`(-)`에 실려 있다. 여전히 완전하지 않으므로 미지 코드는 원값 보존한다.
- **전체 시장 스캔**: 구현 완료. DART는 회사별 조회가 기본이라 종목 수 × API 호출이 되므로
  일일 한도(계정당 20,000회)가 실질 제약이다. 중단·재개(`--resume`), 일일 호출 예산
  (`--max-api-calls`), 이미 저장된 접수번호 건너뛰기로 대응했다. 실측 종목당 5.75회
  (8개월, 대형주 8종목 표본) → 전 종목(3,988) 1년치 ≈ 이틀. 다만 이 값은 대형주
  표본의 참고치이지 상한이 아니므로, 첫 스윕에서 `scan_progress.api_calls`로 실제
  분포를 재고 예산을 다시 잡는다. 아래 참고.

## 사용법

```bash
# 지분 변동 명세 (D001 원문 파싱)
python -m issuer_data collect --market kr --type stake --symbols 005930     --start 2026-08-01 --end 2026-08-31

# 전 종목 스캔 (--symbols 생략 시 DB의 KR 전 종목). 일일 예산에 걸리면 그 자리에서
# 깔끔히 멈추고, --resume 으로 다음 날 이어서 돈다
python -m issuer_data collect --market kr --type stake     --start 2026-01-01 --end 2026-08-31 --max-api-calls 18000
python -m issuer_data collect --market kr --type stake     --start 2026-01-01 --end 2026-08-31 --max-api-calls 18000 --resume

# 진행 상황과 오늘 쓴 호출 수
python -m issuer_data status

# 자기주식 취득/처분 (주요사항보고 B)
python -m issuer_data collect --market kr --type treasury --symbols 005930     --start 2025-01-01 --end 2026-08-31

# 분류 / 딜 집계 / 가격 정합성
python -m issuer_data query --sql "SELECT * FROM v_kr_stake_sales"
python -m issuer_data query --sql "SELECT * FROM v_kr_stake_deals"
python -m issuer_data query --sql "SELECT * FROM v_kr_treasury_price_check"
```

## 전체 시장 스캔 — 설계와 실측

### 왜 재개 가능해야 하는가

전 종목 스캔은 한 번에 끝나지 않는다. OpenDART는 **계정당 하루 20,000회**를 재고
초과하면 그날 키를 막는다. 3,000번째 종목에서 한도에 걸렸을 때 처음부터 다시 도는
설계는 다음 날 예산을 이미 저장된 데이터에 그대로 다시 쓴다는 뜻이라 실용성이 없다.
그래서 세 가지를 넣었다:

1. **종목 단위 커서** (`scan_progress`) — 종목 하나가 끝날 때마다 결과를 커밋한다.
   `--resume`은 완료된 종목만 건너뛴다. **실패한 종목은 건너뛰지 않는다** (다음
   실행에서 재시도되어야 하므로). 커서 키에 **날짜 범위가 포함**되는 게 핵심이다 —
   2025년치를 끝낸 종목이 2026년치까지 끝난 건 아니기 때문이다.
2. **일일 호출 예산** (`api_call_budget` + `--max-api-calls`) — 카운트를 DB에 둔다.
   메모리 카운터는 재실행마다 0으로 돌아가 한도를 그냥 지나친다. 예산이 떨어지면
   `QuotaExceededError`로 스윕을 **중단**한다. 남은 종목을 경고만 찍으며 계속 도는
   것과는 다르다. 이 실행은 `error`가 아니라 `quota` 상태로 기록된다 — 실패가 아니라
   **시킨 대로 멈춘 것**이기 때문이다.
3. **이미 저장된 접수번호 건너뛰기** — DART 공시는 접수되면 불변이고 정정은 새 접수번호로
   올라온다. 따라서 저장된 접수번호의 원문을 다시 열 이유가 없다. 재실행 시 호출량을
   줄이는 가장 큰 요인이다.

**평균 5.75회/종목** (최소 2, 최대 14). 종목당 최소 1회는 D 목록이고, 나머지가
대량보유 보고서 원문이다. 호출 수와 행 수는 비례하지 않는다 — NAVER는 3회로 2,483행이
나왔다 (보고서 하나에 특별관계자가 많으면 행이 폭증한다).

이를 전 종목 **3,988개**(2026-09-04 DART corp_codes 실측)로 확대하면:

- 8개월치: ≈ 23,000회 → **하루 예산을 넘긴다** (이틀, 또는 기간을 쪼개서)
- 1년치: ≈ 23,000회 이상 → **이틀**, 둘째 날 여유는 거의 없다

**이 외삽은 대형주 8종목 기준의 참고치이지 상한이 아니다.** 호출 수를 정하는 것은
시총이 아니라 *대량보유 보고서 건수*, 즉 지분구조가 얼마나 자주 바뀌었느냐다. 대형주
표본이 median보다 공시가 많으리라는 것은 그럴듯한 추측일 뿐, 이 표본에는 중소형주가
한 종목도 없어 중앙값이 더 낮다는 근거가 없다. 소형주는 공시 총량이 적어도 지분변동은
잦을 수 있다. 실제 분포는 첫 스윕에서 `scan_progress.api_calls`로 측정하면 된다 —
컬럼은 이미 채워지고 있다:

```sql
SELECT COUNT(*) n, AVG(api_calls), MIN(api_calls), MAX(api_calls),
       PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY api_calls) AS median
FROM scan_progress WHERE data_type='stake' AND status='done';
```

측정 전까지는 하루 예산을 다 걸지 말고 `--max-api-calls`를 보수적으로 두고
몇백 종목을 먼저 돌려 위 쿼리로 종목당 실비를 확인하는 편이 안전하다.

HANDOFF에서 우려한 "최소 수만 회"보다는 싸다. 이유는 `fetch_stake_changes`가
D 목록에서 `"대량보유"`가 아닌 건은 원문을 열지 않기 때문이다 — 임원·주요주주 보고서가
D 목록의 대다수라 이 필터가 대부분을 걸러낸다.
